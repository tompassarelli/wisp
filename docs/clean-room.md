Wisp is an open-source toolchain and clean-room runtime for Warcraft III maps
([wisp#75](https://github.com/tompassarelli/wisp/issues/75)). The toolchain
builds maps for the official game. The runtime reimplements the behaviour maps
rely on, from scratch, and loads art at run time from the player's own legally
owned Warcraft III install. These rules apply to every
agent and contributor, in code, tests, fixtures, docs, issues, pull requests
and history. The short form is the README's
[Principles](../README.md#principles).

## Rules

- Never distribute Blizzard assets (models, textures, sounds, music, extracted
  data) or Blizzard code (copied or decompiled).
- Decide Wisp's behaviour only from black-box observation of the game as a
  player sees it (pictures, sound, the logs and files the game writes,
  replays, timing, the LAN traffic of games we host) and from public
  documentation. Never from disassembly, decompilation, decrypted or dumped
  executables, debugger sessions, or reading the game's memory.
- No cheating or anti-cheat evasion, and nothing that touches other players'
  games or Blizzard's services.
- No Battle.net login emulation and no DRM bypass. Wisp's online play uses its
  own servers and netcode.
- No Warsmash (AGPL) code; facts only (wisp:docs/warsmash-notes.md).
- No "Warcraft" in a product name; "works with your Warcraft III install" is
  fine.

## Do

- Load models, textures, sounds and data tables from the user's install when
  Wisp runs, through the install-asset loader. Cache extracted files only in
  private local storage outside every repository.
- Commit tests and fixtures made from our own sources: generated files,
  synthetic archives, tones from `ffmpeg`, maps we built. Say in the fixture's
  README how it was made.
- Record measured facts (counts, bounds, timings, file offsets in formats
  the game writes, event order) in new words, with the build they came
  from.
- Implement a native from its signature and from behaviour measured in the
  real game (native fixtures), not from Blizzard's script bodies or the
  game's machine code.
- Name game files by their in-game path (`Units\Human\Footman\Footman.mdx`)
  and let the install supply the bytes.

## Don't

- Commit any file taken from the game or its archives, whole or in part,
  converted or not (`.mdx`, `.blp`, `.dds`, `.wav`, `.mp3`, `.slk`, `.fdf`,
  `.toc`, `.w3x` and the rest), or a picture or recording of it.
- Copy `common.j`, `blizzard.j` or other game scripts. Typed declarations of
  names and signatures (wisp:src/natives/warcraft.d.ts, generated by
  wisp:host/toolchain/natives.ts from the user's own files) are the interface maps
  call and are the only part kept; never commit function bodies, comments
  or the source files.
- Commit game strings, tooltips or other in-game text beyond a short quote
  that identifies something.
- Commit decrypted dumps, disassembly or decompiler output, or addresses
  and offsets inside the game's executable.
- Keep tooling that reads Warcraft's binary or a running game's memory in
  this repo, or decide behaviour from what such a tool showed. If a task
  seems to need it, stop and measure from outside the game instead.
- Emulate a Battle.net sign-in, patch out or work around copy protection, or
  ship a client that does.
- Read Warsmash source to write Wisp code. Use only the facts in
  wisp:docs/warsmash-notes.md, and decide numbers with native fixtures.
- Put "Warcraft" (or Blizzard art or logos) in a product name, icon or logo.

## Smashcraft Servers

Smashcraft Servers is the one change any of our code may make inside a
running game. Patch 3.0 left no route from outside the game to LAN on the live
build (wisp:docs/relay.md, "Reaching players"), so on 25 October 2026 Tom
approved the same kind of in-game LAN switch W3Champions has run for most
active Reforged players for years, as an opt-in in smashcraft-client. It is
allowed only as follows:

- **The switch.** smashcraft-client turns on Warcraft III's LAN network
  provider in the running game, and only after the player opts in to
  "Smashcraft Servers", offered beside Battle.net. The opt-in says Smashcraft
  changes how Warcraft connects while it runs and that Blizzard has not
  approved it. Without the opt-in the client never touches the game.
- **The scan.** Locating the LAN provider on a Warcraft build is done only on
  our own offline pool clients, which hold no Battle.net account; never on a
  signed-in client or a player's.
- **The offline provider write.** On a build that has no LAN provider to
  turn on, writing the missing provider into the running game is allowed
  only on our own offline test clients, which hold no Battle.net account
  (Tom, 25 October 2026). No player build and no signed-in client may use
  it; letting players use it needs a new decision from Tom after it works
  offline.
- **The test.** Before any player sees a switch build, it passes end to end on
  a spare signed-in test account of ours.

Nothing else is allowed: no other read or write of game memory, no reading
hidden game state, no sending or changing match input, no anti-cheat evasion
(a refused or detected switch reports unavailable and stops), nothing in
ranked or ladder play, and no W3Champions code; their FLO is a reference for
behaviour only. What the scan, switch or offline provider write shows never
decides Wisp's or Smashcraft's behaviour.

The switch's addresses, offsets, byte patterns and procedure live in a private
repository and ship compiled inside the client. The offline provider write's
internals live in the same private repository and never ship in any client.
Wisp, Smashcraft and smashcraft-client are public: their code, issues, pull
requests and docs see only the interface (enable the LAN provider, returning
ok or an error), and the rest of this page applies to them unchanged.

After a Warcraft patch the switch may stop working. It accepts only builds it
was checked on, so on a new build Smashcraft Servers reports itself
unavailable and Battle.net play is unaffected until a new scan and test admit
the build.

## Private tools

Private test tools stay private. Two local tools exist only for testing on our
own machines and test accounts: the LAN switch that lets our own test clients
offer LAN games, and the desync debugger that inspects our own clients. They
live outside every repository, under `~/.local/share/wisp-private/`, and never
feed Wisp's implementation; the LAN switch's player form is Smashcraft
Servers, above. The LAN switch loads through
wisp:host/lan/plugin.ts; nothing else in Wisp imports private code.
Their addresses, offsets, dumps, byte patterns and procedures are never
committed, posted in issues or pull requests, or quoted in docs. What they show
may help diagnose our own bugs (such as a desync); it never decides how Wisp
behaves.

## The check

wisp:host/checks/cleanRoom.ts runs before every push and in CI. Unless
wisp:clean-room-allowlist.tsv lists the path as `original` or `generated`
with how it was made, it refuses:

- game-format files (by extension or leading bytes);
- files up to 2 MB with more than 20 JASS declaration lines, like a copy of
  `common.j` or `blizzard.j`;
- memory-access system calls and paths: the Linux process-memory calls,
  the process-trace call, a process's `mem` file under `/proc`, and the
  Windows calls that read, write, re-protect or inject into another
  process's memory;
- address or offset tables for the game binary: three or more lines that
  pair an address, offset, base or relative-address name with a hex value;
- decomp-style symbol names (two to four letters, an underscore, then an
  `80` address);
- imports of `wisp-private` code other than the LAN plugin loader,
  wisp:host/lan/plugin.ts.

A refusal names the file and the rule: delete the material, regenerate it
from our own source, or load it from the install. On 13 October 2026 the
pushed history was rewritten to remove the former engine debugger, the LAN
switch's memory code and the docs that described them; for anything found
later, open an issue.
